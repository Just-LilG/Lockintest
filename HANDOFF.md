## Calculator bug pass (2026-11-16, on 0.28.0; version not bumped)

Compiled `Calc.kt` + `CalcTools.kt` + `CalcModel.kt` with kotlinc 2.0.21 and ran 88 JVM tests (78 existing + 10 new, all pass) plus ~250 hand-written sums and key sequences. The engine (`Calc.kt`) was correct on everything tried; the first four bugs were in the key/model layer (`CalcModel.kt`):
- **(−) after an answer** carried on from Ans, so `2+3= (−)5=` gave 0. `type()` has a `fresh` flag and the (−) key uses it: it now starts a new negative number. The − operator key still carries on.
- **= pressed again** re-read the rounded display text: `1÷3 = = ×3 =` gave 0.9999999999999 and the 1/3 form was lost. `equals()` now leaves an answer alone.
- **×10ˣ** typed a bare `E`, which is the variable E (0): `5= ×10ˣ 2=` gave 0 and `×10ˣ 3=` gave 0. New `typeExp()`: after an answer `Ans×10^`, after a number `E`, otherwise `1E`.
- **Paste** turned every comma into a decimal point (`1,000` became 1.000 = 1, `12,345.5` was a syntax error, `gcd(12,18)` was broken). New `tidyPaste()` strips thousands separators (commas or spaces), keeps argument commas, and still reads `3,14` as 3.14.
- **a/b key** typed a plain `÷`. It now types `/` (the ÷ key still types ÷; `/` carries on from Ans like the other operators). `CalculatorScreen.styledSum()` draws digits over digits as a raised numerator, a fraction slash and a lowered denominator (same text length, so the caret and taps line up); any other `/` is drawn as ÷. It is raised/lowered, not a stacked fraction: a stacked one needs a custom input layout. Not compiled against the Android SDK, so check it on a device.
- **Input line** printed ` =` after the sum once answered (`2+3 =`). `inputText` no longer adds it. The `=` pill in the tool row is separate: it types an equals sign into the sum on purpose (for SOLVE and comparisons).
- **Statistics page crashed** on one value (the sample deviation is NaN) and on a flat line's `r`. `Calc.format` now throws `CalcException` for NaN and infinity instead of letting `BigDecimal` throw a `NumberFormatException`, and the pages' `show()` prints `—` for a figure that does not exist.
- **Matrix determinant** of `[[1,2,3],[4,5,6],[7,8,9]]` was 6.7E-16; pivots below 1e-12 of the largest entry now count as zero.
- **Solver** returned fake roots for `e^x=0` (−30, then −1024 where e^x underflows to 0) and 0 for `3=3`. A root must now be one the function grows away from (`genuine()`), and an identity says "True for every x". Known and left: tiny-scale roots such as `x³=1E-30` still come back as 0 (the residual test is absolute).
- **Deep nesting** (a long paste of `(` or `−`) overflowed the stack and crashed. `Calc`, `BaseN` and `CalcComplex` evaluators catch `StackOverflowError` and report "Too complex", and a paste is cut at 1000 characters.
Regression tests are at the end of `CalcModelTest.kt` and `CalcToolsTest.kt`. The Compose screens were not run (no device here); only read.
Known and left alone on purpose: after an error the broken sum stays and the next key edits it (Casio behaviour, see 0.18.2); NORM-2 shows 1E12 and up as scientific; sin(30) shows 1/2 in MATH display.

## What it is

LockIn is a native Android app (Kotlin, Jetpack Compose) for study partners. Two people pair up, and the core feature is locking your partner's phone for a set time. Around that sit app limits, planned sessions, chat, daily goals, stats and a study kit.

- Package `com.godbless.lockin`, versionCode 74, versionName 0.28.0, minSdk 26, compile/target 35.
- Kotlin 2.0.21, AGP 8.7.3, Gradle 8.9, Compose BOM 2024.12.01, JDK 17.
- Backend: Supabase project `huhhzfbmsdajkppllako` (Auth, Postgres with RLS, Storage, one Edge Function). No Supabase SDK in the app: plain HTTPS in `data/PartnerRepository.kt`.
- Push: Firebase Cloud Messaging, data messages sent by the `push` Edge Function.

## Backend

Tables: profiles (display_name, goal_minutes, lock_allowed, lock_max_seconds), partnerships, messages, typing_status, sessions, device_tokens, usage_settings, usage_days, app_limits, partner_locks, planned_sessions. RLS is on everywhere. All logic is in SECURITY DEFINER RPCs that only `authenticated` can run. The full schema notes are in `supabase/partners.sql` (comments list every migration and RPC).

Polling, not realtime: Home refreshes locks every 20 s (6 s while a lock runs) and immediately on a push (`lockPing`).

Push: `supabase/functions/push/index.ts` (v7, verify_jwt off, it authenticates itself). It needs the secret `FIREBASE_SERVICE_ACCOUNT`. The app sends `messageId` after saving an event message (`pushAsync`); the function words it and the app builds the notification, staying quiet while in the foreground.

### The lock feature (the MVP)

- One lock per target person at a time, owned by the server's clock: `starts_at`, `ends_at`, `ended_at`, `ended_by` (time, locker, emergency, unpaired).
- Options on a lock: message (140 chars), strict (no unlock requests), together (locker starts their own session), start delay (0 to 7 days), extend (+5 to 60 min), pickups reported by the locked phone, unlock request with reason and answer (approve or "not yet", five-minute cooldown).
- Rules per person: `lock_allowed` and `lock_max_seconds`, enforced in `lock_partner` and `lock_extend`.
- RPCs: lock_partner, unlock_partner, lock_ask, lock_answer, lock_report, lock_extend, lock_emergency, their_lock, my_lock, lock_history, lock_rules, lock_rules_set.
- Chat events (also drive pushes and `lockPing`): lock_set, lock_planned, lock_canceled, lock_lifted, lock_extended, asked_unlock, unlock_denied, emergency_release.
- Client: `LockState` (state and actions), `RemoteLockRepository` (RPC calls), `LockPartnerPage` (composer, live card, scheduled card, history, rules, plus `LockEntryCard` used on Home and the Partner tab), `PartnerLockScreen` (what the locked person sees), and the glue in `HomeScreen` (search for `partnerLocked`, `locks.mine`, `showLockPage`).
- Debug: `adb logcat -s LockInLock` prints each lock request and result.
- All lock RPCs were tested against the real pair in a rolled-back transaction (impersonating both users). The Android UI for v2 and scheduled locks has not been compiled or run yet.

## Build, install and update

- Build: `./gradlew assembleDebug` (or release). Needs `local.properties` and `app/google-services.json`.
- Release signing: run `scripts/make-signing-key.sh` once (creates `~/lockin-release.jks` and root `keystore.properties`, both git-ignored). Back the key up: every future update must use the same key. Debug and release keys differ, so uninstall the debug build once before the first release install.
- Full APK update: `scripts/publish-update.sh app.apk "note"` uploads to the `updates` bucket and rewrites `latest.json`.
- Code-only update: `scripts/publish-dynamic.sh` (dex, signature-checked). It only applies when the STABLE_API hash matches, and that hash covers the manifest, resources, `build.gradle.kts`, `google-services.json`, `libs.versions.toml` and the `dyn/` sources. So any manifest or build-file change needs a full APK install.
- 0.6.1 adds `NotifyActionReceiver` to the manifest, so it needs a **full APK** install (a code-only update won't apply).

## 0.28.0: Textbooks redesigned, and explain a selection (2026-11-16)

From the owner: better UI/UX for the books page on phones and tablets, and an AI feature to select a word or sentence and have it explained in relation to the book. Not compiled here (kotlinc diff shows only the usual Compose/coroutines cascades). Not device-tested.

**Explain a selection (reader, `study/PassageAi.kt`, `study/PdfReader.kt`).**
- PDFs are pictures here (PdfRenderer has no text layer below Android 15), so the selection is a region, not text: the crop is sent to the vision model with the whole page for context. That also works for scanned books, equations and figures.
- How you select: press and hold a word (haptic; a word-sized box appears), keep the finger down and drag over a sentence, or tap **Select** in the bottom bar (select mode: one-finger drag selects instead of scrolling; a lime hint pill at the top with ×), or "Explain a word or sentence" in the AI sheet menu. After you let go, two round handles adjust the box and a floating bar offers **✦ Explain**, **Ask** and ×. A tap elsewhere clears it; Back clears it.
- Gesture code: the reader's Initial-pass `awaitEachGesture` now decides between a handle drag, select mode, a long press (`withTimeoutOrNull(longPressTimeout)` with no movement past touch slop, then `dragSelect`), and scroll/pinch (zoom unchanged). Everything a selection touches is consumed, so the list doesn't scroll and no tap fires. Positions map screen ↔ page with `list.layoutInfo` (`item.offset - viewportStartOffset`), `hs.value` and `leftPad` (`fractions`, `selRect`).
- `PageSel` stores page + fractions (zoom-independent). `snipForAi` (AiPages.kt) cuts it from the reader's 1600 px drawing with a margin, enlarges tiny ones to 520 px, caps at 1100 px, JPEG 82. It never recycles the cached page (copies when the cut is the whole page).
- The sheet (`PassageSheet`): a bottom sheet on phones (max 86% height; the page scrolls the selection up near the top first), a 440 dp right-hand panel on wide screens (the pages re-centre in the space left). It contains:
  - "You selected" with the crop and the words the AI read.
  - What it means / Here in the book / For example / Key words, with a skeleton while loading.
  - "Make a flashcard" (question from the text, answer = meaning, the crop as the card's picture) and Copy.
  - Follow-up chips (Simpler, Another example, Why does it matter here?, Test me) and an "Ask about this…" field; follow-ups show as a chat-like thread (your ask on the right, dots while waiting) and send `prior` so answers don't repeat.
- Saved to AI history as `AiKind.Passage` ("Selections" filter): data holds text/meaning/context/example/terms/thread/rect and the crop's file name under `filesDir/.../snips/` (`AiHistoryStore.snipFile`, deleted with the entry or the book). `PassageBody` in AiHistoryUi shows it.
- A one-time tip pill in the reader (`ReaderTips`, prefs `reader_tips`) explains long-press.
- Reader also: on screens ≥ 600 dp pages are read at max 820 dp wide and centred (were stretched across the tablet); the paper tone moved to a pill in the top bar; the bottom bar is page · Select · AI · Card.

**Server (`supabase/functions/ai`, deployed as v7).** New task `passage`: `pages` = that one page, `snip` = the crop (base64), `mode` explain | simpler | example | ask, `question` (ask), `prior` (≤1500 chars). Images are labelled ("THE SELECTED PART…", "The whole page… for context") via a new optional `Page.label`. Reply `{text, meaning, context, example, terms:[{term, meaning}], answer}`; empty when neither meaning nor answer. Same Groq → Gemini hedge, allowance and refund as the other tasks. Client: `AiRepository.passage`, `AiPassage`.

**Textbooks page (`study/LibraryScreen.kt`, rewritten; same signature).**

## 0.23.0: Word Duel and a live tic-tac-toe (2026-11-15)

From the owner: build Word Duel, and make tic-tac-toe live (see the partner's held mark and finger, lower latency).

**Live channel (`live/`).** No new dependency. `WebSocketLite` is a small RFC 6455 client (tested against a local Python server); `LiveChannel` speaks the Phoenix v1 protocol to `wss://<host>/realtime/v1/websocket?apikey=<publishable key>&vsn=1.0.0`, joins the private topic `live:<partnership id>` with the user's JWT, sends a heartbeat every 25 s, reconnects with backoff (0.8 to 15 s) and rejoins every 45 min to renew the token. `acquire()`/`release()` are ref-counted (4 s grace). Authorisation is by RLS policies on `realtime.messages` using `public._live_ok(topic)`: only the pair's two members can listen or send. `HomeScreen` provides it as `LocalLive`. Games treat it as optional: if it is down they fall back to polling (5 s when live is up).

**Authoritative game state stays on the server** (security-definer RPCs). The live layer only pre-announces and nudges: `*_drop` / `wd_try` let the receiver animate before the server confirms, `*_moved` makes it fetch at once, `incomingOpt` is an optimistic copy cleared by a newer `rev` or after 3.5 s, `*_undo` reverts if the sender's RPC fails.

**Tic-tac-toe (`lock/TicTacToe.kt`).** Events `ttt_here/bye/touch/drop/undo/moved`. You see your partner's finger (a dot) or the mark they hold, lifted with a shadow and following their finger (70 ms tween), a highlight on the square they hover, a dashed socket where it came from; the static mark is hidden at their held cell. Touch is throttled to 30 ms with fraction coordinates, so different screen sizes line up. Their slide flight starts from their last seen finger position.

**Word Duel (`lock/WordDuel.kt`, `lock/WordBank.kt`, `data/WordDuelRepository.kt`).** One partner sets a secret 5-letter word (optional clue chip), the other has 6 tries; roles swap each round. Guesser scores 7 minus tries on a solve; the setter scores 2 on a fail. The setter watches the guesser type live (`wd_type`), flips happen on both phones together (`wd_try` then confirm), the setter can send floating emoji (`wd_react`). Marks use a greens-first two-pass algorithm, identical on the server (`_wd_mark`) and the client (`wdMarks`, JVM-tested against known cases). The server JSON is per viewer (`_wd_json`), so the guesser's phone never holds the word until the round ends. Words: `assets/words5.txt` (allowed guesses) and `answers5.txt` (secret picks for "Pick for me"), generated from a frequency list with a manual blocklist, so a few odd words or names may remain. Not on the lock cover.

**Chat.** The Game attach tile opens a picker (`GamePicker` in `home/ChatGame.kt`); `ChatWordCard` shows a round in the thread; invites say "Word Duel" for kind `wd`. A hidden event `game_move|wd|<set|solved|failed|next>` drives push (suppressed if the partner was seen within 9 s).

## 0.22.0: tamper handling (2026-11-15)

From the owner: a fast person could still switch a permission off before the guard reacted, and the aim is "no loopholes" with no PC, no reset, no ADB. Stock Android can't do that without device owner (checked against the docs again: device owner needs a factory-reset phone plus QR/ADB; Family Link is account-level and skipped by extra profiles; screen pinning can be exited and ends on reboot; Play Integrity needs a Cloud project and ignores resets). So the plan is three layers: harder to do, impossible to hide, and a cost for it.

**1. Harder to do (`lock/SettingsGuardService.kt`).** The race had three parts: Android batched the guard's events (`notificationTimeout` 150 ms), the guard then waited 180 ms for the page to settle, and only then looked. Now:
- `notificationTimeout` is 40 ms (`res/xml/settings_guard_config.xml`; a resource change, so full APK install).
- On `TYPE_WINDOW_STATE_CHANGED` from a Settings-like package, if the event's title/class names LockIn or is a device-admin/uninstall class (`looksHeldBack`), a plain opaque **shield** (accessibility overlay, not focusable) goes up at once, the look follows immediately, and the shield is removed if the page is harmless. It is held up to 700 ms while the page has barely drawn (so an unrendered page isn't judged empty) and is always gone after 1.5 s.
- Looks are at most one per 100 ms (`scanBurst`; the first of a burst is immediate), not a 180 ms wait.
- A poll every 500 ms (`pollOnce`) looks again if no event did in the last 1.2 s, only while the screen is on, paired, and a Settings-like package is in front.
- `classify(seen, cls)`: first Android's English wording (`classifyEnglish`, unchanged, says exactly which thing it is), then language-independent fallbacks when "lockin" is on the page: class contains `deviceadmin` (and the admin is on) = Admin; `uninstall`, `installedappdetails`, `appinfo`, `appdetails` = Uninstall; a page with one or two switches (one on) while overlay, usage access or the guard is on = `Other` ("change this on your phone"; the partner's Allow for `other` opens it). Pages whose class contains `notification` are exempt from that last rule.

**2. Impossible to hide (`lock/ProtectionWatch.kt`).** Every 3 s, from `GuardService` and from the guard's poll: overlay, usage access, device admin and the guard are compared with "was seen on". On to off, without the partner's Allow window open and with no lock running, it queues `protect_tamper|<kind>` (kinds `overlay_off|usage_off|admin_off|guard_off`), delivered as soon as there is a session (queue is kept on the phone, so cutting the internet first hides nothing; one entry per kind). `safe_mode` is queued when `BOOT_COUNT` jumped by 2 or more since LockIn last looked (a start-up LockIn never saw). During a lock the lock service still reports (`lock_tamper`), so the two don't double up.
- `GuardService` now runs whenever the phone is **paired** (`Guard.watching` = `Protection.on`), not only with limits, so the watch survives the accessibility guard being switched off. `Protection.update` calls `Guard.sync` when pairing changes. Notification text changed to "Keeping your protection on, holding app limits and sharing app time." The loop ticks every 3 s when there are no limits (was 20 s).
- `device_ping` every 2 minutes from `GuardService` keeps the partner's "seen ..." (already shown per device in the partner screen) fresh; it goes stale when LockIn is stopped or uninstalled.

**3. A cost (server, migration `20261124_tamper_void.sql`, APPLIED as `tamper_void_0_22_0`; push function redeployed as v20).**
- `partner_locks.voided_at/void_kind`. `lock_tamper()` and the new `protect_tamper()` void the running lock (or the one that ended within the last hour, for a warning that was queued offline) for the kinds in `_void_kind`: `admin_off, overlay_off, usage_off, guard_off, safe_mode, time_changed`. A voided lock writes no session (`_lock_to_session` skips it, and `_lock_void` deletes one already written); the phone does the same (`LocalLock.voided`, checked where `HomeScreen` records the finished lock). `stopped`, `silent` (went quiet) and `emergency_dial` only warn: a dead battery or a call for help must not cost hours.
- `protect_tamper()`: needs a pairing; one note per kind per 15 minutes. Chat note `protect_tamper|<kind>`; wording in `home/PartnerState.kt`, `push/Push.kt` and the push function. Void notes end with "That session won't count."
- Tested: `_void_kind` truth values, `_lock_void` on a random user (no-op), columns and functions exist. Not tested with two real accounts (no way to sign in as them here).

**Where I did not follow the plan.** No constant server heartbeat for limits: locks already check in every 15 s and the server's `_silent_check` warns after 4 minutes, but for a phone with no lock a silence can't tell "off for the night" from "LockIn stopped", so a push on silence would fire every night. The partner sees "seen <ago>" instead and judges.

**Risks I could not check (nothing was built or run on a device):**
- Type check: only 2 new errors against the last run, both the unresolved-coroutines cascade (`Dispatchers`, `scope.launch` in `SettingsGuardService.pollOnce`). `ProtectionWatch` and the rest add none.
- False alarms: opening any page titled "LockIn" flashes the shield for a moment. LockIn's own notification page, reached from a notification's long-press, may be asked for as "this" (it has an on switch); through App info it was already held back. `safe_mode` can false-alarm if the phone is restarted twice before LockIn gets to look (same property as the lock's own check).
- Battery: the poll runs twice a second while the screen is on and the phone is paired, but a full look (up to 700 nodes) from the poll happens at most every 1.2 s and only on a Settings-like page. Lower event batching means more events reach the guard from all apps; they return immediately unless the package is Settings-like.
- A person who is quick enough with the first tap of a new page can still win a few tens of milliseconds; what then gets past is reported and costs the session.
- Full APK install needed (accessibility config changed).

## AI speed pass (2026-11-16): `ai` function rewritten + phone-side caching. Server deployed (`ai` v6)

**Deployed on the live project as `ai` v6 (verify_jwt true); a `warm` call answers `{ok:true, keys:2}`.** The app half ships in the 0.25.6+ builds and works against either server version (an old server answers `warm` with a 400, which the app ignores).

Server (`supabase/functions/ai/index.ts`, tested with a Node harness that mocks Groq/Gemini/Supabase: parallel parts, key failover, hedge, cancel, learning, refunds):
- **Parallel parts.** Quizzes/cards are split into 2 to 4 parts (about 3 questions or 4 cards each, at most 5 pages each) written at the same time and merged, interleaved, repeats dropped (`plan`, `groqTask`). With few pages every part reads them all and is told which half/third to draw from. At least 60% of the asked count must come back, else it falls to Gemini.
- **Key pool.** `private.ai_keys` rows `groq`, `groq2` (already in the live DB), `groq3`, `groq4` + optional comma-separated `GROQ_API_KEY`. Parts take turns across keys; a 429 puts a key to rest for its Retry-After (a 401/403 for ten minutes); resting keys go last, and a wait of up to 3.5 s for one is still preferred over leaving Groq. The key list is re-read every 10 minutes. Log lines name `key1`/`key2`.
- **Gemini hedge.** If Groq hasn't answered after `AI_HEDGE_MS` (default 9000) Gemini starts too and the first usable answer wins (the other is aborted); if Groq fails outright Gemini starts at once. Replies carry `via` and `ms`.
- **Less thinking.** `reasoning_effort: "none"` is sent to Groq; a 400 switches that (and JSON mode) off for the request and, once a retry works, remembers it per model.
- **Startup.** The user check (cached 90 s) and key load run together; Groq starts while the daily allowance is counted (over the limit just drops the work). `task: "warm"` does no AI work: loads keys and opens the connection to Groq.
- To add a key: `insert into private.ai_keys (name, value) values ('groq3', '<key>') on conflict (name) do update set value = excluded.value, updated_at = now();`

Phone: `study/AiPages.kt` keeps about 5 MB of prepared page pictures (keyed by book, file size/time, page) and packs JPEGs on other cores while the PDF renderer draws the next page; `data/AiRepository.kt` has `warm()` (at most every 4 min) and retries once, after 1.2 s, on a fast 502/503/504; `ReaderAiSheet` warms the AI and prepares the current page, then quietly the other pages a quiz would use, while it is open.

## Floating-window escape closed (0.6.3)
- Exploit (owner's screenshots): a limited app (TikTok) opened in a floating "small window" kept working. The block screen was an Activity, so the floating app sat over it, or the block screen itself got shrunk into a small window. Detection also only tracked the newest resumed app, so once LockIn's block screen resumed, TikTok (still resumed in its floating window) was forgotten.
- `ForegroundWatcher` now tracks every app screen on screen (`onScreen`, `resumedAt`); on Android 10+ a screen leaves only on ACTIVITY_STOPPED (an unfocused floating window reports Paused but is still visible).

## Safe mode alert
- Android counts every start-up (`Settings.Global.BOOT_COUNT`), safe mode included, but LockIn can't run in safe mode. `LocalLock.noteBoot()` runs on each start-up during a lock (EarlyBootReceiver, direct boot) and when LockService starts; if the count jumped by 2+ since LockIn last saw it (set, beat or boot), a start-up was missed: safe mode.
- LockService then adds one escape and sends `lock_tamper|safe_mode|<minutes away>` instead of `stopped`. Chat: "<name> restarted their phone into safe mode for 14m during the lock"; push (v13 in repo): "restarted into safe mode for 14m during the lock you set".
- Server: `20261113_tamper_safe_mode.sql` adds the kind to `lock_tamper` (tested locally). Until it's applied the server refuses the kind and the warning waits in the queue.

## 0.8.3 — voice player fixes

- **Stuck pause button after a note ended.** Cause: `setOnCompletionListener { stop() }` sat inside `MediaPlayer().apply { }`, so `stop()` resolved to `MediaPlayer.stop()`, not `VoicePlayer.stop()`. The player stopped but `VoicePlayer.playing` stayed set, so the bubble kept the pause icon, and tapping it called `pause()`/`seekTo()` on a stopped player (IllegalStateException). Now completion calls `finished(mp)` → `stop()` (back to idle, bar at 0, next tap replays from the start), pause/resume are wrapped so a dead player resets to idle, and a 50 ms ticker also ends playback if the callback never arrives.
- **Frozen bar / stuck spinner after scrolling.** The ticker and the download used the bubble's `rememberCoroutineScope`, which is cancelled when the bubble leaves the list. `VoicePlayer` now owns its scope (`toggle` is no longer `suspend`).
- Chat: the message area is clipped so the "newest" button cannot slide over the composer.
